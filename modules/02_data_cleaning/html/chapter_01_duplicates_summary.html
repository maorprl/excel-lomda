1הבעיה העסקית

Operations שולחת export של שורות הזמנה לחודש April. הקובץ עומד להזין sales summary, ולכן לפני שמסכמים Units או Line_Revenue צריך לבדוק שה־row-level key מתנהג כמו key אמיתי.

השאלה האנליטית: האם יש ערכים שחוזרים במקום שבו ציפינו ל־uniqueness, ואם כן — האם מדובר בשורה כפולה שאפשר להסיר או ב־data conflict שאסור למחוק אוטומטית?
Define Grain→Test Key→Isolate Repeats→Compare Rows→Classify→Decide→Validate

2Grain & Key

What should one row represent?
תשובה

One row represents one order line.

כל שורה היא line item אחד בתוך הזמנה. לכן ה־grain הוא Order Line.

How do we know?

אותו Order_ID יכול להופיע בכמה שורות עם מוצרים שונים. זה מתאים למערכת יחסים של Order אחד עם כמה Order Lines.

Which field should behave as the row-level key?
תשובה

Line_ID אמור להיות unique ברמת השורה.

Order_ID הוא parent key ולכן repetition שלו לא מוכיחה duplicate.

Trap: repeated value אינו בהכרח duplicate. קודם בודקים אם השדה אמור להיות unique ב־grain הנוכחי.

3בדיקת uniqueness עם COUNTIF

Visual scan לא מספיק כשיש הרבה שורות. אנחנו רוצים helper column שנותנת לכל row את מספר הפעמים שבהן ה־Line_ID שלה מופיע בטווח המלא.

COUNTIF(range, criteria)

ב־worksheet הנתונים נמצאים בשורות 36:96, ו־Line_ID בעמודה A. לכן הנוסחה בשורה הראשונה של הנתונים היא:

=COUNTIF($A$36:$A$96,A36)
$A$36:$A$96

ה־range המלא. ה־$ נועלים row ו־column כדי שהטווח לא יזוז בזמן Fill Down.

A36

ה־criteria של השורה הנוכחית. הוא נשאר relative כדי להפוך ל־A37, A38 וכן הלאה.

פירוש התוצאה: 1 = ה־key מופיע פעם אחת. >1 = repeated key שדורש בדיקה נוספת.

Structured Reference — חלופה כשעמודת העזר נמצאת בתוך Excel Table

=COUNTIF([Line_ID],[@Line_ID])

הנוסחה הזו מתאימה רק כאשר Line_ID_Count היא באמת חלק מה־Excel Table. אם היא מחוץ ל־Table, השתמש ב־A1 references או ב־table-qualified reference.

Formatting troubleshooting

אם התוצאות מופיעות כ־$1.00 ו־$2.00, הנוסחה לא שגויה — התא פשוט קיבל Currency format. תקן דרך Right Click → Format Cells → General או Number.

4Detection ≠ Classification

אחרי שמסננים Line_ID_Count > 1, עדיין לא יודעים אם הרשומות הן exact duplicates. עכשיו משווים את שאר ה־source fields.

Duplicate key with conflicting attributes

5Sanity Check / Validation

אחרי ה־COUNTIF אפשר להריץ detector שני ועצמאי:

Home → Conditional Formatting → Highlight Cells Rules → Duplicate Values

בחר רק את תאי הנתונים של Line_ID. התוצאה הוויזואלית אמורה להצביע על אותם repeated keys שמצאת דרך Line_ID_Count > 1.

COUNTIF

נותן count, אפשר לסנן, למיין ולהשאיר audit trail.

Conditional Formatting

נותן quick visual scan ומשמש cross-check מהיר לשיטה העיקרית.

Validation pattern: שתי שיטות שונות שמצביעות על אותו subset מגדילות את הביטחון שלא טעית בטווח, ב־formula reference או בסינון.

6Remove Duplicates — כלי ניקוי, לא detector

Remove Duplicates הוא כלי מובנה:

Data → Remove Duplicates

הוא מגדיר duplicate לפי העמודות שסימנת. לכן הבחירה ב־columns משנה את משמעות הפעולה.

All source columns selected

Excel מחפש שורות שזהות בכל עמודות המקור. ב־dataset הזה פעולה כזו מסירה שורה אחת — העותק הנוסף של ה־exact duplicate.

Line_ID only

Excel בודק רק את ה־key. ב־dataset הזה הוא היה מסיר שתי שורות מתוך ה־repeated keys — ובכך עלול למחוק אחת משתי גרסאות ה־L0034 באופן שרירותי.

Safe practice: עבוד על copy, בדוק מה נבחר ב־dialog, תעד row count לפני/אחרי, ובמקרה של conflict אל תשתמש ב־Line_ID alone כבסיס למחיקה.

7חלופות והקשרים שימושיים

IF — מסווג, לא מזהה בעצמו

=IF(COUNTIF($A$36:$A$96,A36)>1,"Duplicate","OK")

IF רק מתרגם את תוצאת COUNTIF ל־label. הוא לא מחליף את מנגנון הזיהוי.

FILTER — מוציא subset דינמי

=FILTER($A$36:$J$96,COUNTIF($A$36:$A$96,$A$36:$A$96)>1,"No duplicates")

ב־Excel 365 הנוסחה יכולה להחזיר רק את השורות שה־Line_ID שלהן חוזר. זה shortcut נוח, אבל בפרק הזה COUNTIF helper → Filter נשארה השיטה המרכזית כי היא יותר audit-friendly.

#SPILL!: FILTER היא Dynamic Array formula. כתוב אותה מחוץ ל־Excel Table ובאזור ריק לחלוטין, עם מקום לכל השורות והעמודות שיישפכו.

אותו pattern ב־SQL

SELECT *, COUNT(*) OVER (PARTITION BY Line_ID) AS Line_ID_Count FROM orders;

זה אותו רעיון אנליטי: לכל row מחשבים כמה פעמים ה־key שלה מופיע. ואם רוצים רק את ה־keys שחוזרים:

SELECT Line_ID, COUNT(*) AS cnt FROM orders GROUP BY Line_ID HAVING COUNT(*) > 1;
Transferable concept: הכלי משתנה בין Excel ל־SQL, אבל pattern החשיבה נשאר: define grain → test key behavior → isolate anomalies → inspect context.

Independent Variation — למה Order_ID שונה?

אם מריצים את אותו COUNTIF על Order_ID, נקבל לא מעט counts מעל 1. זה לא מצדיק מחיקה.

Why? Order_ID מזהה Order, אבל ה־grain של הטבלה הוא Order Line. לכן Order אחד יכול להכיל כמה rows לגיטימיים. זו דוגמה לכך ש־duplicate detection תמיד תלוי ב־business grain.

8Common Mistakes & Traps

Repeated = Duplicate

לא נכון. repeated parent key יכול להיות תקין לחלוטין.

COUNTIF > 1 = Exact Duplicate

לא נכון. זה רק repeated key; צריך להשוות את שאר השדות.

Remove Duplicates blindly

מסוכן. התוצאה תלויה ב־columns שסומנו.

Moving range

אם לא נועלים את full key range, Fill Down משנה את טווח הבדיקה ויוצר logic שבור.

Visual scan only

טוב ל־quick check, פחות טוב ל־repeatability ו־audit trail.

RTL confusion

כיוון הגיליון לא משנה את משמעות ה־references. $A$36 נשאר absolute reference בלי קשר למיקום הוויזואלי.

Model Analyst Workflow

Define the grain: one row = one order line.
Identify expected unique key: Line_ID.
Build a repeatable check: COUNTIF with fixed range.
Filter the anomalies: Line_ID_Count > 1.
Compare source fields: exact duplicate vs key conflict.
Validate independently: Conditional Formatting.
Choose action based on evidence: remove only when the duplicate definition is justified.
Preserve evidence: keep raw columns and work on a copy before destructive cleaning.

Key Takeaway

Duplicate cleaning is not “find repeated values and delete them”.
קודם מגדירים grain ו־key, אחר כך מזהים repeated keys, משווים את הרשומות, מסווגים את הבעיה, ורק אז מחליטים אם להסיר, לחקור או להשאיר.
