Data Structure

להבין מה הנתונים מייצגים לפני שבוחרים נוסחה, PivotTable או כלי אחר ב־Excel.

Workbook sheet: 01_DATA_STRUCTURE Difficulty: Foundation Capability: Grain · Identifier · Measures · Dimensions

מטרת הפרק

קיבלת טבלת עסקאות אחת. בשלב הזה לא מחשבים שום דבר. המטרה היא להבין מה מייצגת הטבלה ומה התפקיד של כל שדה, ורק אחר כך לבחור דרך ניתוח.

עקרון עבודה: לפני SUMIFS, PivotTable או כל חישוב אחר — מגדירים קודם את Grain, ה־Identifier, ה־Measures וה־Dimensions.

חמש השאלות והתשובות

1. What does one row represent (the grain)?
תשובה

One row represents one transaction.

כל שורה מתארת עסקה נפרדת. זהו ה־Grain של הטבלה.

2. Which field is the strongest row-level identifier?
תשובה

Transaction_ID

זה השדה שמזהה את העסקה ברמת השורה. לעומת זאת, Customer_ID יכול לחזור ביותר מעסקה אחת.

3. Which measures already exist in the table?
תשובה

Units ו־Unit_Price

אלה שדות מספריים שמשמשים בחישובים. חשוב לזכור: שדה מספרי לא בהכרח נכון לסכם בכל מצב; קודם מבינים את המשמעות העסקית שלו.

4. Which dimensions could be used to group or filter the data?
תשובה

Date, Customer_ID, Product, Category, Region

אלה שדות שאפשר להשתמש בהם כדי לחלק, לקבץ או לסנן את העסקאות. לדוגמה: מכירות לפי Region או לפי Product.

5. For the question “Which product generated the highest revenue?”, which fields are required, and is a new metric needed?
תשובה

נדרשים Product, Units, Unit_Price.

כן. צריך ליצור מדד חדש:

Revenue = Units × Unit_Price

לאחר מכן צריך לצבור את ה־Revenue ברמת Product ורק אז לזהות את המוצר עם הסכום הגבוה ביותר.

Transaction→Revenue per row→Group by Product→Sum Revenue→Highest

המושגים המרכזיים

Grain

מה שורה אחת מייצגת.

כאן: עסקה אחת. זו אחת השאלות הראשונות שכדאי לשאול בכל Dataset לא מוכר.

Identifier / Key

שדה שמזהה רשומה או ישות.

כאן Transaction_ID הוא המזהה החזק ביותר ברמת השורה.

Measure

ערך מספרי המשמש למדידה או חישוב.

כאן: Units, Unit_Price.

Dimension

שדה שמשמש לקיבוץ, פילוח או סינון.

לדוגמה: Product, Category, Region.

Derived Metric

מדד שאינו קיים במקור וצריך לחשב.

כאן: Revenue = Units × Unit_Price.

Grain Change

מעבר מרמת פירוט אחת לרמת ניתוח אחרת.

בשאלה 5 עוברים מ־Transaction grain ל־Product grain באמצעות aggregation.

איך לחשוב כמו Data Analyst

  • אל תתחיל מהפונקציה. קודם להבין את הנתונים ואת רמת הפירוט.
  • מספר לא אומר בהכרח Measure לסיכום. למשל מחיר ליחידה דורש הקשר לפני שמבצעים עליו aggregation.
  • Identifier יכול לחזור ברמה אחרת. Customer_ID חוזר כי לקוח יכול לבצע כמה עסקאות.
  • שאלה עסקית יכולה לדרוש Metric חדש. אם אין Revenue, צריך לזהות את השדות שמאפשרים לבנות אותו.
  • לפני Ranking צריך Aggregation נכון. “Highest revenue product” דורש Revenue כולל לפי Product, לא את העסקה הבודדת הגבוהה ביותר.
טעות נפוצה: לראות את המילה “highest” ולחפש מיד MAX. קודם צריך לבדוק באיזה Grain השאלה מבקשת את התשובה.

חמש השאלות והתשובות

1. What is the likely role of each of the three support sheets?
תשובה

02A_SALES_RAW — Raw transactional sales data.

02B_PRODUCTS_REF — Product reference / lookup table.

02C_REPORT_OUTPUT — Calculated report output / KPIs.

2. Which sheet appears to contain source-level transactional data?
תשובה

02A_SALES_RAW.

הראיה היא שכל שורה מייצגת Order נפרד ויש בה שדות אירוע כמו Order_ID, Date, Customer_ID, Product_ID, Units ו־Revenue.

3. Which sheet appears to be a reference / lookup table, and what entity does one row represent there?
תשובה

02B_PRODUCTS_REF.

כל שורה מייצגת Product אחד, המזוהה באמצעות Product_ID. שאר השדות מתארים את המוצר: שם, Category ו־Standard Price.

4. Which sheet contains derived output rather than raw source data? What evidence supports that conclusion?
תשובה

02C_REPORT_OUTPUT.

התאים של ה־KPIs מכילים נוסחאות שמפנות ל־02A_SALES_RAW, ולכן הערכים הם Derived Output ולא רשומות מקור.

ב־Workbook הנתון, בחלק מהתצוגות התוצאות עלולות להיראות ריקות משום שאין cached values שמורים — אבל הנוסחאות עצמן קיימות.

5. If you were asked to add a new analysis, which sheet(s) would you avoid modifying first, and why?
תשובה

כדאי להימנע קודם כל משינוי 02A_SALES_RAW ו־02B_PRODUCTS_REF, משום שהם משמשים כנתוני מקור ו־Reference.

שמירה עליהם ללא שינוי מגינה על Data Integrity ועל יכולת ה־Audit. עדיף ליצור Sheet ניתוח נפרד או לעבוד באזור Output מתאים.

במקום להסתפק במה שמוצג בתא, אפשר לבדוק את הנוסחה עצמה. אלה הנוסחאות שנמצאות ב־Workbook:

כלי Excel שימושיים ל־Workbook Mapping

המטרה כאן היא לא רק להכיר את שם הכלי, אלא לדעת איך להגיע אליו בפועל כשפותחים Workbook לא מוכר.

איך מגיעים:
Formulas → Formula Auditing → Show Formulas

קיצור דרך ב־Windows: Ctrl + `

מה זה עושה: מציג את הנוסחאות על כל ה־Sheet במקום התוצאות. שימושי לסריקה מהירה של אזורים חישוביים.

Go To Special → Formulas

איך מגיעים:
Home → Find & Select → Go To Special → Formulas

דרך מהירה: Ctrl + G → Special → Formulas

מה זה עושה: מסמן בבת אחת את כל התאים שמכילים formulas, כדי לראות איפה נמצאת הלוגיקה ב־Sheet.

Trace Precedents

איך מגיעים:
בחר תא עם נוסחה → Formulas → Formula Auditing → Trace Precedents

מה זה עושה: מצייר חצים אל התאים שמהם הנוסחה מקבלת מידע ועוזר להבין dependencies בין אזורים ו־Sheets.

סדר עבודה מומלץ: Go To Special → Formulas כדי למצוא את התאים החישוביים → Show Formulas כדי לקרוא את הלוגיקה → Trace Precedents כדי להבין מאיפה הנתונים מגיעים.

המושגים המרכזיים

Raw / Source Data

רשומות המקור ברמת האירוע או העסקה. לרוב כדאי לשמור אותן נקיות משינויים ידניים.

Reference / Lookup Table

טבלה שמתארת ישויות ומאפיינים שלהן. היא לא “טבלה עם XLOOKUP”; היא טבלה שממנה אפשר לבצע Lookup.

Derived Output

תוצאות שנוצרו מחישוב, aggregation או formula שמבוססים על נתוני מקור.

Dependency

קשר שבו תא או Sheet אחד מסתמך על נתונים ממקום אחר. זה חשוב במיוחד לפני שינוי מבנה הקובץ.

Data Integrity

שמירה על נתוני המקור בצורה עקבית ואמינה כך שאפשר יהיה לבדוק, לשחזר ולאמת את הניתוח.

Workbook Mapping

מיפוי התפקיד, ה־Grain והקשרים של ה־Sheets לפני שמתחילים לבצע עבודה אנליטית.

איך לחשוב כמו Data Analyst

  • אל תסמוך על שמות Sheets. בדוק את המבנה בפועל.
  • שאל “מה כל שורה מייצגת?” גם ברמת Workbook. Grain עוזר לזהות אם Sheet הוא עסקאות, מוצרים או Output.
  • Formula היא ראיה. נוסחאות שמפנות לנתוני מקור הן סימן חזק ש־Sheet הוא Derived.
  • שמור Raw ו־Reference נקיים. עבודה חדשה עדיף לבצע ב־Analysis/Output נפרד.
  • מפה dependencies לפני שינוי. אחרת אפשר לשבור formulas או דוחות בלי להבין למה.
טעות נפוצה: לפתוח Workbook, לבחור מיד Sheet שנראה “נכון”, ולהתחיל לערוך. קודם ממפים את המבנה ואת הקשרים בין ה־Sheets.

Tables vs Ranges

לזהות מתי אזור נתונים הוא Excel Table אמיתי ומתי הוא רק ordinary range — ומה ההבדל הזה אומר מבחינת שמות, structured references, הרחבה אוטומטית ו־audit של Workbook לא מוכר.

Workbook sheet: 03_TABLES_RANGES Difficulty: Foundation Capability: Excel Tables · Ranges · Structured References

מטרת הפרק

שני אזורי נתונים יכולים להיראות כמעט זהים, אבל מבחינת Excel הם יכולים להיות שני דברים שונים לגמרי:

Excel Table
Defined Excel object

אובייקט מוגדר עם שם, headers, filters, structured references והתנהגות של auto-expansion.

Ordinary Range
Cell range

קבוצת תאים רגילה. היא יכולה להיות מעוצבת כמו טבלה, אבל אין לה את ההתנהגות והמטא־דאטה של Excel Table.

עקרון עבודה: אל תחליט לפי הצבעים בלבד. כדי להוכיח שמדובר ב־Excel Table צריך לבדוק את Excel עצמו — במיוחד את Table Design ואת Table Name.

3. What clues in the Excel interface prove that the object is a Table?
תשובה

הראיה החזקה ביותר היא שכאשר לוחצים בתוך A16:E21, מופיעה לשונית Table Design, ובתוכה מופיע Table Name מוגדר: tbl_Sales_03.

Filters, headers ו־banded rows הם clues נוספים, אבל הם אינם הוכחה בפני עצמם — כי אפשר להוסיף אותם גם לטווח רגיל.

5. Why can Table names and structured ranges matter when auditing an unfamiliar workbook?
תשובה

שמות Tables ו־structured references הופכים formulas ליותר קריאות, ניתנות ל־audit וקלות לתחזוקה.

לדוגמה, =SUM(tbl_Sales_03[Revenue]) אומר במפורש מה מסכמים, בעוד =SUM(E17:E21) אומר רק איפה נמצאים התאים.

בנוסף, structured references יכולים להמשיך לכלול שורות חדשות כאשר ה־Table מתרחב.

אובייקט Excel מוגדר שמכיל נתונים במבנה טבלאי וכולל שם, headers ויכולות אוטומטיות.

Ordinary Range

טווח תאים רגיל כגון H16:J20. עיצוב חזותי לא הופך אותו ל־Table object.

Table Name

שם האובייקט של הטבלה. בתרגיל: tbl_Sales_03.

Structured Reference

הפניה לפי Table ועמודה, למשל tbl_Sales_03[Revenue], במקום כתובות תאים בלבד.

Auto-expansion

היכולת של Table להתרחב כאשר מוסיפים שורה חדשה בצמוד לטבלה.

Auditability

היכולת להבין במהירות מאיפה נוסחה מקבלת נתונים ומה משמעות הטווחים שהיא משתמשת בהם.

איך לחשוב כמו Data Analyst

  • אל תסתפק בעיצוב. בדוק האם מדובר ב־Table object אמיתי.
  • חפש את Table Name. שם טוב הוא רמז משמעותי למבנה ה־Workbook.
  • שים לב ל־structured references. הן עוזרות להבין formulas מהר יותר.
  • חשוב על refreshability. Table שמתרחב אוטומטית יכול להפוך ניתוח ליותר robust.
  • ב־audit, metadata חשוב. לא רק הערכים בתאים — גם סוג האובייקט והשם שלו מספרים איך הקובץ בנוי.

Keys & Relationships

להבין איך datasets מתחברים זה לזה לפני שעושים XLOOKUP, Merge או JOIN: מה ה־grain של כל טבלה, מהו ה־key הנכון, איפה הוא צריך להיות unique, ומהי cardinality של הקשר.

חמש השאלות והתשובות

1. What does one row represent in Sales, Products, and Customers?
תשובה

Sales: one order line / sales line. Products: one product. Customers: one customer.

2. Which field should connect Sales to Products?
תשובה

Product_ID.

Sales.Product_ID→Products.Product_ID
3. Which field should connect Sales to Customers?
תשובה

Customer_ID.

Sales.Customer_ID→Customers.Customer_ID
4. On which side of each relationship should the key be unique?
תשובה

ה־key צריך להיות unique בצד ה־reference / dimension:

  • Products[Product_ID] צריך להיות unique.
  • Customers[Customer_ID] צריך להיות unique.
  • ב־Sales, אותם IDs יכולים להופיע פעמים רבות.
Products (1)→Sales (M)
Customers (1)→Sales (M)
5. Would Order_ID alone be a safe row-level key in Sales? Explain from the data shown.
תשובה

לא. Order_ID אינו unique ברמת השורה. לדוגמה O1001 מופיע ב־L001 וב־L002.

Order_ID מזהה הזמנה, אבל Line_ID הוא ה־row-level identifier החזק יותר ב־Sales.

1:M ומה המשמעות שלו

1:M — One-to-Many אומר שרשומה אחת בצד אחד יכולה להיות קשורה להרבה רשומות בצד השני.

Products → Sales

מוצר אחד יכול להימכר בהרבה sales lines. לכן Product_ID unique ב־Products, אבל חוזר ב־Sales.

Customers → Sales

לקוח אחד יכול לבצע הרבה רכישות. לכן Customer_ID unique ב־Customers, אבל חוזר ב־Sales.

ומה זה M:M? קשר many-to-many הוא מצב שבו שני הצדדים יכולים להופיע פעמים רבות זה מול זה. בדרך כלל משתמשים בטבלת ביניים כדי לייצג קשר כזה בצורה נקייה.

הקשר ל־XLOOKUP ול־JOIN

ה־relationship וה־key הם הרעיון. XLOOKUP, Power Query Merge ו־SQL JOIN הם דרכים שונות לממש אותו.

Relationship+Key→XLOOKUP / Merge / JOIN
דוגמה: כדי להביא את Category של מוצר אל Sales, מחברים את Sales.Product_ID אל Products.Product_ID. רק אחרי שהבנו שה־key תקין ו־unique בצד Products, בוחרים כלי מימוש.

מה חשוב לבדוק לפני Lookup / Join?

  • Grain: מה כל שורה מייצגת בכל dataset?
  • Join key: איזה שדה קיים בשתי הטבלאות ומתאר את אותה ישות?
  • Uniqueness: האם ה־key באמת unique בצד שאמור להיות ה־1?
  • Missing keys: האם יש Sales rows שאין להן התאמה ב־Products או Customers?
  • Duplicates: אם ה־reference key כפול, Lookup עלול להיות ambiguous ו־Join עלול להכפיל שורות.

Key Takeaway

Grain → Key → Relationship → Uniqueness → Tool.
אל תתחיל מ־XLOOKUP. קודם תבין את מבנה הנתונים. אם ה־relationship לא נכון, גם נוסחה תקינה יכולה להחזיר תשובה מטעה.

Dependency Chain

Net_Revenue לא עומד בפני עצמו. הוא תלוי בחישוב קודם, שגם הוא תלוי בשדות מקור.

Units+Unit_Price→Gross_Revenue+Discount→Net_Revenue
Gross_Revenue = Units × Unit_Price
Net_Revenue = Gross_Revenue × (1 - Discount)
Dependency שואל: על אילו values או calculations החישוב הזה נשען — ישירות ובעקיפין.

תשובה

Source / Raw: Line_ID, Order_ID, Product, Region, Units, Unit_Price, Discount.

2. What is the dependency chain for Net_Revenue?
תשובה

3. Are the formulas consistent down each calculated column?
תשובה

Gross_Revenue — כן. הנוסחה עקבית לאורך העמודה.

Net_Revenue — לא. תא אחד שובר את pattern של הנוסחאות.

Q4 שואל: איפה בדיוק נמצאת החריגה?
5. Why would treating a derived field as raw source data be risky during a take-home assessment?
תשובה

כי אפשר לפספס formulas שבורות, values שהוקלדו ידנית ו־dependencies שלא יתעדכנו. אז אפשר לבסס analysis על נתון שנראה תקין אבל אינו אמין.

Suggested answer: Treating a derived field as raw data can hide calculation errors, hardcoded values, and broken dependencies, which can lead to incorrect analysis and make the workbook harder to audit.

למה I20 הוא מלכודת טובה?

Formula cell

Hardcoded cell

“המספר אולי נכון, אבל אני לא סומך על התא הזה עד שאני מבין למה הוא hardcoded.”

1. From the summary, what field is acting as the row dimension?
תשובה

Region.

איך יודעים? שורות ה־summary הן North, South, West. אלה ערכים של השדה Region ב־source data. לכן זה ה־field שמחלק את התוצאה לשורות.

Rows → Region

למה לא Date או Product? גם Date וגם Product הם dimensions אפשריים, אבל הם לא נמצאים כרגע בתפקיד של row dimension. אם Product היה ב־Rows, היינו מצפים לראות Laptop Pro, Mouse X, Laptop Air וכדומה.

5. If the displayed value were “% of Grand Total” rather than the raw sum, where would you verify that in a real PivotTable?
תשובה

Value Field Settings → Show Values As, ושם לבדוק אם מוגדר % of Grand Total.

למה זו לא אותה בדיקה כמו שאלה 4? כי יש שתי שכבות שונות:

Summarize Values By

עונה על השאלה: איך Excel מחשב את ה־measure?

Revenue → SUM → 1410

Show Values As

עונה על השאלה: איך Excel מציג את התוצאה שחושבה?

1410 / 2570 → 54.9%

למשל North:

Grand Total = 1410 + 210 + 950 = 2570
North % of Total = 1410 / 2570 ≈ 54.9%

ה־aggregation הבסיסי עדיין יכול להיות Sum of Revenue; רק display calculation מציג את ה־sum כאחוז מה־Grand Total.

הניסוח הנכון: Revenue was summarized using Sum, and the summarized value was displayed as % of Grand Total.

טעות נפוצה: לראות 54.9% ולהגיד “Revenue הוא 54.9%”. האחוז הוא אופן הצגת ה־measure המסוכם, לא ה־raw Revenue עצמו.

Validation — איך בודקים שה־summary הגיוני?

גם אם זה snapshot, אפשר לבצע reconciliation מהיר מול ה־source. זה בדיוק הרגל טוב ל־take-home: אל תסתפק בקריאת ההגדרות — תבדוק שהמספרים מסתדרים.

1. Revenue total: 1200 + 90 + 950 + 150 + 120 + 60 = 2570
2. Regional totals: 1410 + 210 + 950 = 2570
3. Order counts: 3 + 2 + 1 = 6, תואם ל־6 source rows.
4. Percent check: 54.9% + 8.2% + 37.0% ≈ 100% (פער זעיר יכול לנבוע מעיגול).
למה זה מקצועי? Pivot settings יכולים להיראות סבירים ועדיין להיות שגויים. reconciliation פשוט נותן שכבת ביטחון נוספת שה־output עקבי עם ה־source.

איך זה היה נראה ב־PivotTable אמיתי?

אם היית מקבל workbook עם PivotTable חי, תהליך discovery טוב היה נראה כך:

  1. לחץ בתוך ה־PivotTable. ודא ש־Excel מזהה אותו כ־Pivot object.
  2. פתח Field List. בדוק מה נמצא ב־Rows, Columns, Filters ו־Values.
  3. בדוק את ה־source. PivotTable Analyze → Change Data Source.
  4. בדוק כל measure. Value Field Settings → Summarize Values By.
  5. בדוק display transforms. Value Field Settings → Show Values As.
  6. בדוק filters / slicers. מספר יכול להיות “נכון” רק לתת־קבוצה של הנתונים.
  7. בדוק Refresh. ודא שה־Pivot מעודכן מול ה־source הנוכחי.
  8. בצע reconciliation. השווה totals מרכזיים ל־source או לחישוב עצמאי.
מבחן החשיבה: “North = 1,410” היא רק התוצאה. ה־discovery הוא להבין האם 1,410 נוצר מה־source הנכון, ב־Region grain, דרך Sum of Revenue, ללא filters נסתרים וללא display transform ששינה את המשמעות.

='[Pricing_Master.xlsx]Rates'!$B$2

יש source ברור: Workbook → Sheet → Cell.

אחרי Break Link

ייתכן שנשאר רק value. לא ברור מאיפה הוא הגיע, והוא לא יתעדכן מהמקור.

הבעיה: פתחת Workbook — אבל האם אתה באמת רואה את כל ה־source?

ב־Excel, שורה או עמודה שלא נראית יכולה להיות לא־גלויה מכמה סיבות שונות. Filter יכול להוציא rows מהתצוגה, row יכולה להיות hidden ידנית, קבוצה יכולה להיות collapsed, ו־column שלם יכול להיות מוסתר.

5. Why could analyzing only the visible cells produce a misleading answer?
תשובה

כי ה־visible cells מייצגים כרגע רק חלק מה־source. אם תפרש אותם כ־full dataset, Counts, Totals, averages ואפילו conclusions לפי Region/Product יכולים להיות חסרים או מוטים.

Filter population: 5 Active records.
Visible population: 4 records — בגלל ש־L005 מוסתרת בנוסף.

ה־nuance: Filter עצמו אינו “שגיאה”. אם השאלה העסקית היא Active transactions only, ה־filter יכול להיות מכוון. הבעיה היא שאתה צריך לדעת שה־filter קיים, ולוודא שגם כל ה־Active records שאמורים להיכלל באמת נכללים.

הסיכון האמיתי: לתת תשובה על visible population בזמן שאתה חושב שנתת תשובה על business population.
6. What visibility checks should you complete before trusting counts or totals?
תשובה

צריך לבצע visibility audit קצר לפני שסומכים על Count או Total. המטרה אינה רק “לחשוף הכול”, אלא להבין במדויק איזה population קיימת, איזה חלק נראה, ואיזה חלק החישוב כולל.

1. Check active filters and criteria. בדוק אם יש filter פעיל, על איזה field, ואיזה values/conditions נבחרו. כאן: Status = Active.
2. Reconcile total rows to filter-matching rows. כמה records קיימים ב־source, וכמה אמורים להישאר אחרי ה־filter? כאן: 7 → 5.
3. Reconcile filter-matching rows to actually visible rows. אם המספר עדיין שונה, חפש manual hidden rows או collapsed groups. כאן: 5 → 4 בגלל L005.
4. Inspect manually hidden rows. חפש gaps במספרי השורות, למשל 21 ואז 23. אל תניח שכל gap נוצר מה־filter.
5. Inspect Group / Outline state. חפש controls של +/- או outline levels. Group יכול להסתיר כמה rows בלי לשנות את ה־filter.
6. Inspect hidden columns. חפש gaps באותיות העמודות. כאן Column M מוסתרת ומכילה Product_ID.
7. Inspect the calculation itself. בדוק אם ה־formula כוללת את כל rows, רק filtered rows, או רק visible rows. Visibility של המסך ו־population של formula הן שתי שכבות נפרדות.
8. Match the population to the business question. אחרי שהבנת את המצב הטכני, ודא שזה באמת ה־population שהתבקשת לנתח.
תשובה טובה ל־assessment: Before trusting counts or totals, I would identify active filters and their criteria, reconcile total versus visible rows, inspect manually hidden or grouped/collapsed rows, check hidden columns, verify how the calculation treats filtered/hidden records, and confirm that the resulting population matches the business question.

איך להעריך אם Workbook שקיבלת מאדם אחר נמצא במצב שאפשר לסמוך עליו — לפני שאתה משנה formulas, מרענן נתונים או “מתקן” מספר שנראה חשוד.

Workbook sheet: 17_WORKBOOK_HEALTH Difficulty: Intermediate Capability: Workbook Health Audit Core risk: Healthy-looking ≠ Healthy

הסיטואציה: ה־Workbook נראה תקין — אבל יש clues שמחייבים verification

ב־Exercise 12 אתה מקבל Workbook “בירושה”. ה־KPIs מוצגים, אין מסך מלא ב־errors, וחלק מהמספרים אפילו נראים הגיוניים. אבל יש כמה clues שונים: formula שמפסיקה מוקדם מדי, timestamp ישן, handoff note על Calculation Mode, ו־evidence היסטורי של #REF!.

Q1–Q6 — תשובות מלאות

1. Which KPI formula appears to have incomplete source coverage?
תשובה

Total Revenue. הנוסחה היא =SUM(C18:C21), בעוד שה־source ממשיך עד C22.

איך יודעים? משווים את גבולות ה־formula לגבולות ה־source. אם ה־source מכיל Revenue גם ב־C22, אבל formula עוצרת ב־C21, השורה האחרונה לא נכללת.

למה זה חשוב? כי formula syntactically correct יכולה עדיין לחשב subset לא נכון. זה risk של coverage, לא של syntax.

טעות נפוצה: לחשוב ש־“אין error” = “ה־KPI נכון”.

2. Which KPI values are formulas, and which are static/hardcoded evidence?
תשובה

Formulas: Total Revenue, Order Lines, Review Rate.

Static / recorded evidence: Last Refresh, Calculation Mode = Manual, והטקסט Formula: =SUM(#REF!).

למה זה חשוב? כי formula חיה אפשר audit דרך Formula Bar / precedents / recalculation. Static evidence הוא clue שצריך לאמת, לא state שמוכח אוטומטית.

דוגמה מהתרגיל: ה־handoff note אומר Manual, אבל ה־Workbook עצמו כרגע מוגדר Automatic. Recorded state ≠ current verified state.
3. Which recency clue should make you question whether the workbook is up to date?
תשובה

Last Refresh = 2026-06-30.

איך יודעים שזה דורש investigation? ה־source מכיל July records — כלומר data dates מאוחרים מה־timestamp הרשום.

מה לא נכון להסיק? לא נכון לומר מיד שהנתונים stale. ה־timestamp הוא warning, לא proof. אולי הנתונים נוספו ידנית, אולי ה־timestamp לא עודכן, ואולי הוא מתייחס למנגנון refresh אחר.

Freshness clue ≠ freshness conclusion. אנליסט טוב מזהה inconsistency ואז בודק מה באמת התרענן ומתי.
4. Which Excel calculation setting should you verify before trusting displayed formula results?
תשובה

Calculation Mode. המסלול: Formulas → Calculation Options.

אם ה־Workbook נמצא ב־Manual, formula יכולה להמשיך להציג result ישן אחרי שה־inputs השתנו.

Automatic

Input changes→Recalculate→Displayed value updates

Manual

Input changes→May stay unrecalculated→Old value can remain

העיקרון: Check state before changing state. קודם verify, אחר כך decide אם צריך recalculation או שינוי mode.

5. Which recorded formula clue indicates a broken-reference risk in the inherited model?
תשובה

Formula: =SUM(#REF!).

#REF! מעיד על reference שנשבר או חדל להיות תקף. אבל כאן זה recorded clue מהגרסה הקודמת — לא formula חיה שמחזירה error כרגע.

Live error

תא formula אמיתי מציג #REF!. זה current issue.

Recorded clue

תא טקסט אומר Formula: =SUM(#REF!). זה historical evidence שדורש investigation.

טעות נפוצה: לכתוב בדוח “The workbook currently contains #REF! errors” בלי שאימתת שיש error חי.

6. In what order would you validate workbook health before changing formulas?
תשובה

צריך workflow שמפריד בין discovery, verification, recalculation ו־editing. הסדר המומלץ:

1. Understand source boundaries. כמה rows קיימות? איפה source מתחיל ונגמר? מה ה־intended population?
2. Verify Calculation Mode. האם Excel נמצא ב־Automatic או Manual כרגע?
3. Map formulas vs hardcodes. איזה outputs הם calculations חיים ואיזה values הם static / handoff evidence?
4. Check formula coverage. האם כל formula מכסה את כל ה־source שהיא אמורה לכסות?
5. Check freshness / refresh clues. האם timestamps, source dates ו־refresh state עקביים?
6. Investigate broken dependencies. האם יש live errors, historical clues, external links או suspicious hardcodes?
7. Recalculate carefully. רק אחרי שהבנת את ה־state, בצע recalculation מבוקר אם נדרש.
8. Reconcile outputs to source. חישוב עצמאי של totals/counts/rates מול KPIs.
9. Only then edit. עכשיו יש לך evidence מספיק כדי לשנות formula בלי למחוק את ההקשר.

Workbook Health Workflow — גרסת Assessment

Establish the source boundary. Confirm the first and last rows/columns that define the intended population.
Verify calculation state. Check the actual Excel Calculation Mode before trusting displayed results.
Classify evidence. Separate live formulas from hardcoded values, timestamps, notes, and historical clues.
Audit formula coverage. Confirm that formulas extend through the full intended source range.
Assess freshness. Compare refresh clues with source dates and data provenance.
Investigate reference risk. Look for live #REF! errors, external links, or historical broken-reference evidence.
Recalculate deliberately. Recalculate only after you understand the current workbook state.
Reconcile independently. Recompute critical totals, counts, and rates from source data.
Edit last. Change formulas only after the cause of the mismatch is understood and documented.
